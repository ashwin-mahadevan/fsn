Electron exists because the software engineering ecosystem has developed both a (1) fantastic full-stack web development experience, and (2) Chromium and V8, which provide highly-optimized and cross-platform web and javascript runtimes. Because of (1) and (2), it makes more sense to build native apps by running them in a Chromium instance driven by a Node instance; otherwise, developers need to create a version of their app per-platform, and ensure that all of them are well-optimized independently. Electron produces a cross-platform application by packaging a "client" (Chromium) and "server" (Node) written by the developer, and allows the client and server to communicate via inter-process communication. This *almost* gives developers an identical experience web development; however, they are forced to implement communication between the "client" and "server" themselves via Electron's IPC interface. This leaves room for a massive developer experience upgrade: if we setup the IPC transport to act in place of TCP, ie, providing an interface to send HTTP requests and responses directly over IPC, then developers could *literally* use any fullstack framework they'd like and ship it as a native application. We've just patched together an initial proof-of-concept in this directory that works by using electron's `protocol.handle` api to intercept same-origin requests and redirect them to the server running in the main process.

The way I'd like to publish this concept is as a meta-framework alternative to Electron itself called "FSN" (short for Full-Stack Native).

For the MVP:

I'd like developers to be able to run `fsn <project-name> init {sveltekit|nextjs}`. This should create the `./<project-name>` pnpm monorepo, containing a "native" package with the sveltekit/nextjs app, generated by the relevant cli sveltekit/nextjs provide. The root package.json should have only `fsn` as a devDependency, and it should have a "scripts" field defining an object whose entries call our `fsn` CLI:

`fsn build` should first create a /tmp/workdir and copy the "native" subdir. Then, it should run the relevant production build script for svelte/nextjs on the copy, take the output dir and copy it into the /tmp/workdir, and then discard the "native" dir keeping only the build output. It should then should create an application.js file defining the main process for the electron app in the work dir. For the MVP, it doesn't actually need to do the full process of what I had you setup in your investigation; instead, it should just setup the http protocol handler using the server result of the first step, copy the  then spawn a new BrowserWindow and load the homepage (/) file from the result of the build step. Finally, `fsn` build should run the required Electron CLI commands, etc. to produce a production native application, and copy the app back from the temp workdir to the project dir.

This CLI command should read {sveltekit|nextjs} from a `<project-name>/fsn.config.js` also created by `fsn init`. Its default export should be a config object, using jsdocs to type it as a config type we provide ("import('fsn').Config", which should evaluate to `{ type: "sveltekit" | "nextjs" }`, which should be the only consumable module/type exported by `fsn` altogether.).

I've just created ~/fsn. I'd like you to turn that directory into a pnpm monorepo (setting sharedWorkspaceLockfile: false in the pnpm-workspace.yaml), with `packages/cli` (named "fsn" in its package.json so that when we publish,enabling `npx fsn ...`), as well as `apps/examples/{sveltekit|nextjs}`, which should be themselves generated by `fsn init` to serve as examples and to confirm that everything works end-to-end.

The CLI should be implemented as a single file `packages/cli/bin.js` pointed at by the package.json bin field.
